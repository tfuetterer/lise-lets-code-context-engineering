Context Engineering

Wie wir KI-Agenten wirklich schlau machen

Tobias Fütterer · lise GmbH · 2026

🤖

Was ist ein KI-Agent?

Ein KI-Agent ist ein Programm, das selbstständig Aufgaben erledigt — es kann Dateien lesen, Code schreiben, E-Mails senden, Daten analysieren und vieles mehr.

Stellt euch einen digitalen Assistenten vor, der nicht nur antwortet, sondern eigenständig handelt.

Das Problem

„Mach mir eine Pizza."

Wenn wir einem KI-Agenten einfach nur sagen „Mach XY", ist das wie auf der Straße zu einem Fremden zu gehen und zu sagen:

„Back mir eine Pizza."

Er kennt euren Geschmack nicht. Er hat kein Rezept. Er hat keine Küche.
Irgendwas wird rauskommen — aber wahrscheinlich nicht das, was ihr wolltet.

Wie wir das ändern können — genau darum geht es heute.

Was ist Context Engineering?

Context Engineering bedeutet, dem KI-Agenten alles mitzugeben, was er braucht, um gute Ergebnisse zu liefern: Wissen, Werkzeuge, Regeln und Kontext.

📋

Wissen

Hintergrundinfos, Dokumentation, Stil-Vorgaben — alles, was der Agent wissen muss.

🔧

Werkzeuge

Zugriff auf Dateien, APIs, Datenbanken — die Hände des Agenten.

📏

Regeln

Vorgaben wie etwas gemacht werden soll — Qualität, Format, Grenzen.

🎯

Kontext

Was wurde schon gemacht? Was ist das Ziel? Wer ist die Zielgruppe?

Was ist der Context?

Der Context ist alles, was der Agent in einem Gespräch sehen kann — sein gesamtes Arbeitsgedächtnis. Stellt euch ein Whiteboard vor, auf das alles geschrieben wird.

💬

Eure Nachrichten

Jeder Prompt und jede Antwort — die gesamte Konversation.

📄

System-Prompt

Unsichtbare Anweisungen, die das Verhalten des Agenten steuern.

🔍

Tool-Ergebnisse

Alles, was der Agent liest, sucht oder abfragt — Dateien, APIs, Datenbanken.

🧩

Geladene Skills & Regeln

CLAUDE.md, Skills, Agent-Definitionen — alles wird in den Context geladen.

Der Context hat ein Limit — das Context Window. Je besser wir steuern, was reinkommt, desto bessere Ergebnisse bekommen wir. Das ist Context Engineering.

Vier Wege, wie ihr einen KI-Agenten einsetzen könnt — erklärt am Beispiel Pizza.

CLAUDE.md — Die Hausordnung

Die CLAUDE.md ist die zentrale Konfigurationsdatei für den Agenten. Wie eine Hausordnung definiert sie Regeln, Konventionen und Wissen, die immer gelten.

  • Wird automatisch beim Start geladen
  • Definiert Projekt-Konventionen und Coding-Standards
  • Enthält wichtiges Hintergrundwissen zum Projekt
  • Gilt für jede Konversation — ohne dass ihr es wiederholen müsst

Beispiel

„Antworte immer auf Deutsch"

In der CLAUDE.md steht z.B.:
→ Sprache: Deutsch
→ Framework: React + TypeScript
→ Tests vor jedem Commit
→ Keine console.log im Prod-Code

Ohne CLAUDE.md fragt der Agent jedes Mal neu.

Wo lebt die CLAUDE.md?

Die CLAUDE.md kann auf mehreren Ebenen existieren — sie werden alle zusammen geladen.

Kontext Wo? Wie?
User ~/.claude/CLAUDE.md Persönliche Regeln, die in allen Projekten gelten
Projekt CLAUDE.md Projekt-Regeln, die fürs ganze Team gelten
Unterordner src/CLAUDE.md Spezifische Regeln für bestimmte Bereiche des Projekts

Alle Ebenen werden zusammengeführt — von allgemein (User) bis spezifisch (Unterordner).

So sieht eine CLAUDE.md aus

Eine einfache Markdown-Datei im Projekt-Root — kein Frontmatter nötig.

CLAUDE.md
# Projekt: Meine Web-App ## Sprache & Stil - Antworte immer auf Deutsch - Verwende TypeScript mit strikten Typen - Kein `any` — immer konkrete Typen ## Architektur - Frontend: React + styled-components - Backend: Node.js + Express - Tests: Jest + Testing Library ## Regeln - Vor jedem Commit: `npm test` ausführen - Keine `console.log` im Produktiv-Code - Komponenten immer als Function Components

Einfach Markdown — der Agent liest es automatisch bei jedem Start.

Skills — Das Rezept

Ein Skill ist eine wiederverwendbare Anleitung für den KI-Agenten. Wie ein Rezept beschreibt er Schritt für Schritt, was zu tun ist.

  • Vorgeschriebene Arbeitsabläufe
  • Qualitätsstandards eingebaut
  • Einmal erstellt, immer wieder nutzbar
  • Kann von jedem verwendet werden — ohne Technik-Wissen

Beispiel

„Erstelle einen Commit"

Der Skill sorgt automatisch dafür, dass:
→ Tests vorher laufen
→ Die Nachricht auf Deutsch ist
→ Das richtige Format eingehalten wird

Ohne den Skill macht der Agent es „irgendwie".

Wo leben Skills?

Skills können auf zwei Ebenen angelegt werden — als persönliche Skills oder als Team-Skills im Projekt.

Kontext Wo? Wie?
User ~/.claude/skills/ Persönliche Skills, die in allen Projekten verfügbar sind
Projekt .claude/skills/ Team-Skills, die mit dem Projekt versioniert und geteilt werden

Skills sind Textdateien — kein Code, keine Installation. Projekt-Skills werden ins Repo committed.

So sieht ein Skill aus

Ein Ordner mit einer SKILL.md — oben Metadaten, unten die Anweisungen.

.claude/skills/commit-messages/SKILL.md
--- name: commit-messages description: Erstellt standardisierte Commit-Messages. Verwende diesen Skill immer, wenn ein Commit erstellt werden soll. --- # Commit-Messages erstellen Wende diesen Skill an, wenn Commits erstellt werden sollen. ## Vorgehen 1. Prüfe mit `npm test`, ob alle Tests bestehen 2. Schreibe die Commit-Message auf Deutsch 3. Verwende Präsens ("Füge hinzu", nicht "Hinzugefügt") 4. Maximal 200 Zeichen 5. Kein Co-Authored-By Header

name = der /slash-command Name  ·  description = wann der Skill automatisch geladen wird

Sub-Agents — Der Pizzabäcker

Ein Sub-Agent ist ein konfigurierbarer Spezialist — eine Markdown-Datei, die einen eigenen KI-Assistenten definiert: mit eigenem System-Prompt, eigenen Werkzeugen und eigenem Modell.

  • Läuft in eigenem Kontext — belastet nicht eure Hauptsession
  • Bekommt nur die Werkzeuge, die er braucht
  • Kann ein anderes (schnelleres/günstigeres) Modell nutzen
  • Wird automatisch aufgerufen, wenn die Aufgabe passt

Beispiele

Code-Reviewer
→ Darf nur lesen, nicht schreiben
→ Prüft auf Fehler und Stil

Debugger
→ Analysiert Fehler und Stack-Traces
→ Kann Code ändern, um Bugs zu fixen

Wie Spezialisten in einer Pizzeria: Teigmacher, Ofenmeister, Garnierer.

Wo leben Sub-Agents?

Sub-Agents sind Markdown-Dateien mit Frontmatter — persönlich oder im Projekt.

Kontext Wo? Wie?
User ~/.claude/agents/ Persönliche Agenten, die in allen Projekten verfügbar sind
Projekt .claude/agents/ Team-Agenten, die mit dem Projekt versioniert und geteilt werden

Markdown-Datei mit System-Prompt + Werkzeuge + Modell. Projekt-Agenten werden ins Repo committed.

So sieht ein Sub-Agent aus

Eine Markdown-Datei definiert den Spezialisten — Frontmatter konfiguriert, Body instruiert.

.claude/agents/code-reviewer.md
--- name: code-reviewer description: Prüft Code auf Qualität und Best Practices. Verwende nach Code-Änderungen. tools: Read, Grep, Glob, Bash model: sonnet --- Du bist ein erfahrener Code-Reviewer. ## Vorgehen 1. Führe `git diff` aus, um Änderungen zu sehen 2. Prüfe auf logische Fehler und Sicherheitsprobleme 3. Bewerte Lesbarkeit und Namensgebung 4. Gib konkretes, umsetzbares Feedback ## Ausgabeformat - Kritisch: Muss behoben werden - Warnung: Sollte behoben werden - Vorschlag: Kann verbessert werden

tools = nur Lese-Zugriff  ·  model = schnelleres Modell spart Kosten

MCP-Server — Das Handy

Ein MCP-Server gibt dem Agenten Zugang zu externen Informationen und Systemen — wie ein Handy, mit dem er googeln, nachschlagen und kommunizieren kann.

  • Verbindung zu Datenbanken, APIs, Services
  • Zugriff auf aktuelle Informationen
  • Kann mit anderen Systemen interagieren
  • Erweitert die Fähigkeiten des Agenten dynamisch

Beispiel

„GitHub MCP-Server"

Der Agent kann damit:
→ Issues lesen und erstellen
→ Pull Requests prüfen
→ Repository-Infos abrufen

Ohne MCP-Server kennt er nur das, was man ihm direkt sagt.

Wo leben MCP-Server?

MCP-Server werden als externe Dienste konfiguriert — persönlich oder im Projekt.

Kontext Wo? Wie?
User ~/.claude/settings.json Persönliche MCP-Server, die in allen Projekten verfügbar sind
Projekt .mcp.json Team-MCP-Server, die mit dem Projekt versioniert und geteilt werden

MCP-Server laufen lokal oder remote. Projekt-Server werden unter "mcpServers" in der Settings-Datei eingetragen.

CLI Tools als Alternative

Für die allermeisten MCP-Server gibt es auch ein CLI Tool als Alternative — z.B. gh statt GitHub-MCP, jira statt Jira-MCP, curl statt HTTP-MCP.

Der Agent kann diese Tools direkt über die Shell aufrufen — ganz ohne Server-Setup. Oft reicht das völlig aus, bevor man einen MCP-Server aufsetzt.

Context Engineering = Die Kunst, diese Bausteine so zu kombinieren,
dass der Agent genau das liefert, was ihr braucht.
